# ボートレース期待値予測システム 仕様書

Oct 23, 2026 · @くゎんた

## 概要

ボートレースの単勝で「予測勝率 × オッズ」が1を十分に超える艇だけを買い、回収率100%超えを狙う。第1段階は単勝に絞り、効果が確認できてから2連単・3連単へ広げる。

- **対象**: 全国24場の全レース、券種は単勝（第1段階）
- **作るもの**: 公式データの取得・整形、勝率モデル、オッズとの合成、バックテスト、当日の買い目候補の出力（投票は手動）
- **成功の定義（ゲート1）**: 一度も調整に使っていないテスト期間12か月で、回収率105%以上・ベット数1,000件以上・回収率の95%信頼区間の下限95%以上
- **実弾投入の条件（ゲート2）**: ペーパートレード2か月で、購入時オッズと確定オッズのずれ・買い目の頻度がバックテストの想定内に収まる（回収率では判定しない。詳細は「検証」）
- **撤退基準**: どちらかのゲートを満たさない限り、実際のお金は賭けない

## 前提と制約

個人のWindows PCで動かし、データ費用は0円、公式サイトへの負荷は最小限に抑える。

| 項目 | 内容 |
| --- | --- |
| 実行環境 | 実行PCはWindows、開発PCは別でもよい（下記）。Python 3.14。LZH解凍は7-Zip（`7z`）を外部コマンドとして呼ぶ。`lhafile`は3.14向けのWindows用ホイールが無く、ビルドにVisual Studioが要るため使わない |
| データ利用 | 公式サイトのサイトポリシー上、私的使用の範囲を超える複製・頒布は不可。取得データ・学習済みモデルは公開しない |
| アクセス頻度 | サイトポリシーは大量アクセスを禁止事項としている。並列化せず、LZHは2秒に1件、オッズ・直前情報ページは3秒に1件以上の間隔を空ける |
| データ費用 | 0円（公式の無料配布データのみ使用） |
| 賭け金 | 月1万円を上限とし、超えたら買い目を出さない。お金がかかるのはフェーズ4（少額実戦）だけで、検証はすべて仮想購入で行う |
| 投票 | 自動投票はしない。システムは買い目候補を出すだけで、投票は本人が手動で行う |
| 法令・税 | 舟券の購入は20歳以上に限られる。払戻金は一時所得になり得るため、全ベットの収支ログを残す |

**開発・実行環境**

開発PCでコードを書き、データ取得・学習・当日運用は実行PCで回す。データの正本は実行PCに置き、コードだけをGitで行き来させる。

| 項目 | 開発PC | 実行PC |
| --- | --- | --- |
| 役割 | コードの作成、テスト | データ取得、学習、バックテスト、当日運用 |
| データ | 動作確認用の数週間分だけ | 全期間（正本）。外付けドライブ等にバックアップ |
| 電源 | 制約なし | 長時間取得中とレース当日はスリープしない設定 |

- **コード**: GitHubの非公開リポジトリで共有し、実行PCは`git pull`で更新する。`data/`と`models/`は`.gitignore`で除外し、公式データやモデルをリポジトリに入れない
- **Python環境**: 両PCでPython 3.14に揃え、バージョン固定した依存関係ファイルから入れる。7-Zipも両PCに入れる（Macは`7zz`）
- **パス**: データ・モデルの保存先と7-Zipの実行ファイルのパスは`config.yaml`に書き、PCごとに切り替える（WindowsとMacが混在してもよい）。7-ZipのインストーラはPATHを通さないため、Windowsの既定は`C:\Program Files\7-Zip\7z.exe`
- **モデルの受け渡し**: LightGBMの標準のテキスト形式と、T・α・βはJSONで保存する。pickleは使わない
- **取得の重複禁止**: オッズと直前情報は実行PCだけで取得し、開発PCからは取得しない（サイト負荷と取得時間の無駄を避ける）

## データソース

出走表と結果は公式の無料LZHファイル、オッズと直前情報は公式サイトのレースページから取る。過去のオッズは確定オッズしか取れない見込みなので、運用中は締切5分前のオッズも別に記録する。

| データ | 主な中身 | 取得元 | 用途 |
| --- | --- | --- | --- |
| 番組表（B） | 選手登番・級別・年齢・体重、全国/当地の勝率と2連率、モーター・ボートの番号と2連率、締切予定時刻 | `https://www1.mbrace.or.jp/od2/B/YYYYMM/bYYMMDD.lzh`（1日1ファイル、全場分） | 特徴量、当日の予想 |
| 競走成績（K） | 着順、進入コース、展示タイム、ST、レースタイム、天候・風・波、全券種の払戻金 | `https://www1.mbrace.or.jp/od2/K/YYYYMM/kYYMMDD.lzh` | 正解ラベル、選手の履歴特徴量、払戻の照合、直前情報の過去分の代用 |
| 単勝オッズ | 6艇の単勝オッズ | 公式サイトの単勝・複勝オッズページ（場コード・日付・レース番号を指定） | 期待値計算、オッズとの合成 |
| 直前情報 | 展示タイム、展示進入コース、チルト角、部品交換、気象（天候・風・波など） | 公式サイトの直前情報ページ（場コード・日付・レース番号を指定） | 特徴量。過去分の展示タイムと気象は成績ファイルの値で代用する |

- 文字コードはShift\_JIS。全角数字や全角スペースが混ざるため、パース前に正規化する
- 番組表の1行は空白区切りでは分けられない箇所がある（例: モーター2連率とボート番号が `57.14158` のように連結する）。正規表現で桁数を指定して切り出す
- 公式の旧サービス「オッズ情報・結果」閲覧は2025年3月5日に終了している。過去日付のオッズ・直前情報ページが今も見られるかは未確認（リスク参照）

**取得時間の目安（1年分あたり、概算）**

| データ | リクエスト数 | 間隔 | 所要時間 |
| --- | --- | --- | --- |
| 番組表・成績（LZH） | 約730件（1日2ファイル） | 2秒 | 約25分 |
| 単勝オッズ | 約5万件（1レース1ページ） | 3秒 | 約42時間 |
| 直前情報 | 約5万件（1レース1ページ） | 3秒 | 約42時間 |

年間レース数を全24場で約5万と見積もった概算で、フェーズ1で実測して置き換える。LZHは10年分でも数時間で取れるが、オッズと直前情報は合わせて1年分で約3.5日かかる。何年分集めるかが、学習・検証期間を決める。

## データ仕様

すべてのテーブルは`race_id`（日付8桁＋場コード2桁＋レース番号2桁、例: `202610231201`）でつなぐ。保存形式はParquet、元のLZHは`data/raw/`にそのまま残す。

| テーブル | キー | 主な列 | 出典 |
| --- | --- | --- | --- |
| races | race\_id | date, jcd, venue, rno, race\_name, grade, distance, close\_time, weather, wind\_dir, wind\_speed, wave | B（締切時刻）＋K（気象） |
| entries | race\_id, boat | racer\_id, name, age, branch, weight, class, nat\_win, nat\_2r, loc\_win, loc\_2r, motor\_no, motor\_2r, boat\_no, boat\_2r | B |
| results | race\_id, boat | course, exhibition\_time, st, finish（1〜6、失格等はnull）, status（F/L/K/S）, race\_time | K |
| before\_info | race\_id, boat | exhibition\_time, exhibition\_course, tilt, parts\_changed, weather, wind\_dir, wind\_speed, wave, source（`page`または`k_proxy`） | 直前情報ページ、無い期間はKで代用 |
| payouts | race\_id, bet\_type, combo | payout\_yen, popularity | K |
| odds\_win | race\_id, boat, snapshot | odds, fetched\_at（snapshotは`final`または`T-5`） | オッズページ |
| bets\_log | race\_id, boat | p\_model, p\_final, odds\_at\_bet, ev, stake, placed（実際に投票したか）, finish, payout\_yen | システム出力＋本人の記録 |

- 欠場艇はentriesに残し、odds\_winが無いことで判別する
- 同じ日のデータを再取得したら上書きする（当日・前日分は確定前の可能性があるため）

## 特徴量設計

特徴量は「そのレースの締切前に分かっている情報」だけで作る。ボートレースは6艇の比べ合いなので、各指標はレース内の順位や平均との差にも変換する。

| 区分 | 特徴量 | 取得元・時点 |
| --- | --- | --- |
| 枠 | 艇番（1〜6） | 番組表 |
| 選手の期別成績 | 級別、全国勝率・2連率、当地勝率・2連率、年齢、体重 | 番組表 |
| 機材 | モーター2連率、ボート2連率 | 番組表 |
| 直前情報 | 展示タイム、展示進入コース、チルト角、部品交換の有無、風向・風速・波高 | 直前情報ページ（締切前に公開）。過去分の展示タイム・気象は成績ファイルで代用 |
| レース内相対値 | 上記各指標と展示タイムのレース内順位、レース平均との差 | 番組表・直前情報から計算 |
| 選手の履歴 | 直近10走の平均着順・平均ST、直近1年のF回数、艇番別の1着率 | 前日までの成績（K）から計算 |
| 場の特性 | 場コード、場×艇番の1着率、場×風向の1着率、ナイター、レース番号、グレード | 前日までの成績から計算 |

**リークを防ぐ時点ルール**

1. 履歴・場の特性は、そのレース日の前日までの成績だけで計算する（同日の前のレースは使わない）
2. 成績ファイル（K）の値は、締切前に直前情報として公開されるもの（展示タイム・気象）だけを過去分の代用に使う。本番の進入コース・ST・レースタイムは結果なので使わない
3. 展示進入・チルト・部品交換は成績ファイルに無いため、直前情報ページを取得できた期間だけ使い、それ以外は欠損値のままLightGBMに渡す
4. 代用値と実際の直前情報が一致するかを、両方そろう期間で確認する（展示タイムの一致率、気象のずれ）
5. オッズは勝率モデルの特徴量に入れない。オッズとの合成（次節）でだけ使う
6. 学習・検証・テストの分割は日付で行い、同じ日のレースが複数の期間にまたがらないようにする

## モデル

2段構えにする。まず公開情報だけで各艇の勝率を出し、次にその勝率と市場（オッズ）の勝率を合成して、市場が見落としている分だけを取り出す。

**段階1: ファンダメンタル勝率モデル**

LightGBMの二値分類（1着なら1）で各艇のスコア s を出し、レース内でsoftmaxをかけて6艇の合計を1にする。温度 T は検証期間の対数損失が最小になる値に決める。

```latex
p_i = \frac{\exp(s_i / T)}{\sum_{j \in \text{race}} \exp(s_j / T)}
```

**段階2: オッズとの合成（Benter方式）**

単勝オッズから市場の勝率 q を出し（控除分を除くため合計1に正規化）、モデルの勝率と対数で重み付け合成する。重み α と β は検証期間で条件付き最尤推定する。α がほぼ0なら、モデルは市場に何も付け加えていないと判断する。

```latex
q_i = \frac{1/o_i}{\sum_j 1/o_j}, \qquad p^{*}_i = \frac{\exp(\alpha \log p_i + \beta \log q_i)}{\sum_j \exp(\alpha \log p_j + \beta \log q_j)}
```

- 欠場艇は除いて残りの艇で正規化し直す
- 評価は対数損失を「市場の勝率 q だけ」と比べ、q に勝てているかを第一に見る
- 校正は予測勝率を10区分に分け、予測と実際の1着率のずれで確認する

## 買い目決定と資金管理

期待値が1を余裕を持って超える艇だけを、資金の小さな割合で買う。閾値は検証期間だけで決め、テスト期間では動かさない。

```latex
\mathrm{EV}_i = p^{*}_i \, o_i, \qquad f_i = k \cdot \frac{p^{*}_i o_i - 1}{o_i - 1}
```

| ルール | 初期値 | 意味 |
| --- | --- | --- |
| 期待値の閾値 | EV ≥ 1.10 | 推定誤差の分の余裕を持たせる |
| 最低勝率 | p\* ≥ 0.05 | 大穴は推定が不安定なので買わない |
| オッズ上限 | 50倍以下 | 同上 |
| 1レースの点数 | 最大1点（EVが最大の艇） | 第1段階は単純に保つ |
| ケリー係数 k | 0.25 | フルケリーは振れ幅が大きすぎる |
| 1点の上限 | 資金の2%、かつ設定した上限額 | 一度の外れで崩れない |
| 最小単位 | 100円単位で切り捨て、100円未満なら見送り | 舟券の最小購入単位 |
| 日次の損切り | 当日の損失が月予算の10%に達したら停止 | 連敗時の暴走を防ぐ |

単勝の売上は小さいため、自分の購入でオッズが下がる。運用では購入額を控えめにし、締切5分前オッズと確定オッズの差をbets\_logで追う。

## 検証

データを日付で3つに分け、テスト期間は最後に一度だけ使う。閾値や特徴量をいじるのは検証期間までに限る。

| 期間 | 範囲（仮置き） | 使い道 |
| --- | --- | --- |
| 学習 | 2020年1月〜2024年6月 | LightGBMの学習 |
| 検証 | 2024年7月〜2025年6月 | 温度 T、合成の α・β、EV閾値の決定 |
| テスト | 2025年7月〜2026年6月 | ゲート1の判定（一度だけ） |
| ペーパートレード | ゲート1通過後の2か月 | 締切5分前オッズでの仮想購入、ゲート2の判定（実行面のずれの確認） |

範囲はフェーズ1で実際の取得時間を測ってから決める（「データソース」の目安参照）。LZHだけで作れる部分は長い期間で学習し、オッズと直前情報が要る合成・バックテストは、それらを集められた期間に合わせる。頑健性の確認として、月ごとに学習し直して翌月を予測するウォークフォワードも回す。

**評価指標**

- 回収率、ベット数、的中率、最大ドローダウン、月別の収支
- 回収率の95%信頼区間（レース単位のブートストラップ10,000回）
- 対数損失（モデル単体・合成後・市場の勝率だけ、の3つを比較）
- オッズ帯別の回収率（低オッズ・中・高で偏っていないか）

**比較対象**

- 全艇を均等に買う（控除率25%なので回収率およそ75%になるはず）
- 1号艇だけを毎回買う
- 市場の勝率 q だけでEV判定する（理論上ほぼ買い目が出ない。出るなら計算ミスを疑う）

**サンプル数の考え方**

平均オッズ5〜6倍の単勝では、回収率の95%信頼区間は300ベットで約±25ポイント、1,000ベットで約±14ポイントある。回収率105%を100%と区別するには約7,000ベットが必要になる。この判定は件数を無制限に増やせるバックテストで行い、ペーパートレードと実弾は「仮想購入では見えない実行面のずれ」の確認に使う。月1万円・100円単位の実弾（3か月で約300ベット）では、エッジの有無は判定できないし、判定しない。

**ゲート2（ペーパートレード2か月）の判定基準**

1. 締切5分前オッズでEV ≥ 1.10だった買い目のうち、確定オッズで計算し直してもEV ≥ 1.0を保つものが80%以上
2. 締切5分前オッズから確定オッズへの変化率の中央値が、バックテストで使った補正値の範囲内
3. 1日あたりの買い目の件数が、テスト期間の平均の±30%以内
4. 確定オッズで評価した回収率が、テスト期間の回収率の95%信頼区間に収まる（明らかな破綻がないかの確認のみ）

## システム構成

Pythonパッケージ`boatev`1つにまとめ、取得・整形・学習・検証・当日予想をそれぞれコマンドで動かす。上段で検証を通ったモデルだけが、下段の当日運用に使われる。

&#91;embedded content: システム構成 · 取得から当日の買い目まで\]

| コマンド | 役割 |
| --- | --- |
| `boatev download --from 2020-01-01 --to 2026-10-22` | 番組表・成績のLZHを取得（取得済みは飛ばす） |
| `boatev parse` | LZHを解凍・パースしてParquetに保存 |
| `boatev odds --from ... --to ...` | 単勝オッズを取得（中断しても続きから再開） |
| `boatev beforeinfo --from ... --to ...` | 直前情報を取得（中断しても続きから再開） |
| `boatev features` | 特徴量テーブルを作成 |
| `boatev train` | 勝率モデルを学習し、T・α・βを推定 |
| `boatev backtest` | 回収率レポート（HTMLとCSV）を出力 |
| `boatev today` | 当日の買い目候補を表示し、bets\_logに追記 |

```text
boatev/
  boatev/         # download, parse, odds, features, model, backtest, today
  config.yaml     # 閾値・ケリー係数・予算上限・アクセス間隔
  data/raw/       # LZHの原本（B/、K/）とオッズHTML
  data/processed/ # Parquet
  models/         # 学習済みモデルとT・α・β
  reports/        # バックテスト結果
  tests/          # パーサーと計算のテスト（実ファイルのサンプル付き）
```

## 当日の運用フロー

朝に番組表を取り込み、各レースの締切前にオッズを1回だけ取って買い目候補を出す。投票は本人が手動で行い、翌日に結果を照合する。

1. **朝**: `boatev today --prepare` で当日の番組表を取得し、直前情報以外の特徴量を計算しておく
2. **各レースの展示後、締切10〜5分前**: `boatev today --race <場> <R>` で直前情報とオッズを1回ずつ取得し、勝率 p を出し直したうえで合成勝率 p\*・EV・賭け金を表示する。条件を満たす艇がなければ「見送り」と出す
3. **投票**: 本人がテレボート等で手動投票し、`placed`（投票したか）と実際の購入額を記録する
4. **翌日**: 成績ファイルを取得して結果と払戻を照合し、日次収支と「締切5分前オッズ − 確定オッズ」の差を集計する
5. **月1回**: 最新月まで含めて再学習し、ゲートの指標と月予算の消化状況を確認する

## リスクと未確定事項

最大のリスクは「市場がすでに効率的で、取れるエッジが無い」こと。仕組みはそれを早く安く見極めるためにある。

| リスク | 影響 | 対策 |
| --- | --- | --- |
| エッジが無い | 回収率が75〜95%に収まる | ゲート1で止める。お金は失わない |
| 過去日付のオッズ・直前情報が取れない | バックテストができない | フェーズ0で最初に確認。取れなければ今日から記録を始め、ペーパートレード中心に切り替える |
| オッズページのHTML構造が不明 | オッズ取得が壊れる | フェーズ0で実ページを保存し、それを元にパーサーとテストを書く |
| 確定オッズと購入時オッズの差 | バックテストが甘くなる | 運用中は締切5分前オッズも記録し、差を補正値として使う |
| 自分の購入でオッズが下がる | 実際の回収率が下がる | 1点の上限額を低く保つ |
| 閾値いじりによる過学習 | テストで崩れる | テスト期間は一度だけ使う |
| 公式の配布形式の変更・終了 | 取得が止まる | 生データを全て保存しておく |

**決めること**

- [ ] 1点の上限額（月の上限は1万円に決定）
- [x] 学習データの期間: フェーズ1で取得時間を測ってから決める
- [x] 直前情報（展示・チルト・部品交換・気象）を特徴量に入れる

## 実装順序

取得できるかが一番不確かなオッズと直前情報を最初に確かめ、長時間かかる取得をなるべく早く実行PCで走らせ始める。取得を回している間に、開発PCでパーサーとモデルを作る。各ステップは完了条件を満たしてから次へ進む。

| 順番 | 実装するもの | 完了条件 | 主に使うPC |
| --- | --- | --- | --- |
| 1 | リポジトリの雛形（`config.yaml`、依存関係の固定、`.gitignore`、テストの土台） | 両PCで同じ環境が入り、空のテストが通る | 開発 |
| 2 | 事前確認スクリプト: 過去日付のオッズ・直前情報ページを数件取得してHTMLを保存、LZHを1日分取得して解凍 | 取得できる期間が分かる。保存したHTMLとLZHがテスト用サンプルになる。Windowsで7-Zipを使って解凍できる | 実行 |
| 3 | `download`（LZHの取得と解凍） | 1か月分を取得でき、中断しても取得済みを飛ばして再開できる | 開発→実行 |
| 4 | `odds`・`beforeinfo`（ページ取得と生HTMLの保存のみ、パースは後回し） | 1日分を3秒間隔で取得・保存でき、途中から再開できる。ここで取得時間を実測する | 開発→実行 |
| 5 | 長期取得の開始: 実行PCでLZHの全期間、オッズ・直前情報を新しい日付から過去へ順に取得し続ける | 実行PCで取得が回り続けている。以降のステップと並行して進む | 実行 |
| 6 | `parse`（番組表B・成績K → Parquet） | サンプルのLZHで races・entries・results・payouts が正しく出る。払戻金を元ファイルと数件照合 | 開発 |
| 7 | オッズ・直前情報のパーサー（保存済みHTML → odds\_win・before\_info） | 保存したHTMLで6艇分の値が正しく取れる。欠場艇を判別できる | 開発 |
| 8 | 学習期間の決定 | 実測した取得時間から、学習・検証・テストの範囲を仕様書に確定値で書き込む | — |
| 9 | `features` | リーク防止ルールのテスト（前日までの情報しか使っていないこと）が通る | 開発 |
| 10 | `train` 段階1（LightGBM＋レース内softmax） | 検証期間の対数損失と校正の表が出る | 開発→実行 |
| 11 | `train` 段階2（オッズとの合成） | α・βが推定でき、合成後の対数損失を市場の勝率だけの場合と比べられる | 開発→実行 |
| 12 | `backtest`（買い目ルール、分数ケリー、レポート） | 比較対象（均等買いでおよそ75%など）が想定どおりの値になる。検証期間で閾値を決める | 開発→実行 |
| 13 | ゲート1の判定 | テスト期間で一度だけ実行し、結果を記録する。不合格ならステップ9に戻る | 実行 |
| 14 | `today`（当日の買い目候補とbets\_log） | 当日の番組表・直前情報・オッズから買い目候補が出る。ペーパートレード（フェーズ3）を開始できる | 開発→実行 |

「開発→実行」は、開発PCで小さいデータを使って作り、Gitで実行PCに渡して本番データで回すことを指す。ステップ2で過去のオッズ・直前情報が取れないと分かった場合は、ステップ4・5を「今日から毎日記録する」運用に切り替え、ステップ13の前にペーパートレードの記録を貯める。
